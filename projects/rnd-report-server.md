# 빌드·실보드 측정 자동화 플랫폼

## 개요

임베디드 비전 소프트웨어를 릴리스하려면 매번 **소스 빌드 → 실보드 실행 → 성능 측정 → 리포트 작성 → 위키 Publish**를 반복해야 합니다. 기존에는 보드와 고객 프로젝트마다 따로 만든 CI 잡(Jenkins)이 이 일을 나눠 맡고 있었습니다. 이 서버는 그 잡들을 **하나의 서비스로 통합**한 것으로, 웹 UI, REST API, AI 에이전트용 MCP 서버, CLI에서 같은 기능을 제공합니다.

새 프로젝트를 추가하는 일은 YAML 파일 하나를 쓰는 것으로 줄었고, 대시보드에서 보드 상태, 최근 성능, 실행 기록을 한눈에 볼 수 있습니다. 두 실행 결과를 바로 비교하고, 측정값이 이상하면 자동으로 경고합니다.

## 시스템 구조

<figure class="fig"><div class="frame pad"><img src="assets/diagrams/report-server-architecture.svg" alt="빌드·실보드 측정 자동화 플랫폼 구조: 인터페이스, 서비스 계층, 설정·Queue·Worker, 실행 파이프라인"></div><figcaption><b>FIG 1</b><span>서버 구조. 네 가지 인터페이스가 공통 서비스 계층을 거쳐 실행 요청을 Queue에 넣고, Worker가 보드와 장비를 확보한 뒤 7단계 파이프라인을 실행합니다.</span></figcaption></figure>

### 설정 4계층
- 실행 설정은 **플랫폼(보드 종류) → 보드(개별 장비) → 프로젝트 → 실행별 Override** 네 층을 합쳐 만듭니다. 보드는 여러 프로젝트가 함께 쓰므로, 프로젝트에는 보드를 적지 않고 실행할 때마다 고릅니다.
- 보드에 넘기는 실행 인자, 옵션 파일, HIL 시나리오 파일이 모두 설정에서 생성되므로, 빌드마다 사람이 직접 입력할 값이 없습니다.
- 웹에서 바꾼 설정은 주석과 폼 밖의 값을 그대로 둔 채 저장되고, 설정 디렉터리의 Git 이력으로 남습니다.

### 실행 파이프라인
- Preflight → checkout → Docker 빌드 → 입력 생성 → 보드 실행 → 리포트 → Publish. 필요한 단계만 골라 실행할 수 있고, 단계 간 의존성은 자동으로 검사합니다.
- 단계 정의는 **테이블 하나**에 모아 두었고, Runner, 화면, 폼, 검사가 모두 이 테이블을 읽습니다. 테이블과 구현이 어긋나면 테스트가 잡아냅니다.
- Worker는 프로젝트별로 하나씩 순서대로 실행하며, 보드, 측정 포트, HIL 캡처 카드를 **lease**로 확보한 뒤 진행합니다. 실패하거나 취소되면 원인을 기록하고, 재시도하거나 같은 설정으로 새로 실행할 수 있습니다.
- cron 형식의 **Scheduled run**을 지원하며, 지난번 성공한 실행과 커밋이 같으면 건너뜁니다.

## 측정 · 비교 · 리포트

- **보드 실행**: HIL 장비로 주행 영상 시나리오를 재생하면서 보드 소프트웨어를 실행하고, FPS, 지연, CPU(kDMIPS), 메모리, DDR 대역폭, NPU 점유율, 스레드별 CPU를 측정합니다.
- **녹화**: 보드의 결과 스트림을 ffmpeg로 녹화하고, CAN 출력 확인 도구 화면을 가상 디스플레이(Xvfb)에서 녹화해 실행 페이지에서 바로 재생합니다.
- **비교**: 두 실행의 핵심 지표, 빌드와 설정 차이, 단계별 프로파일링 표를 Baseline 대비 변화량과 함께 나란히 보여 줍니다. 리포트를 만든 코드로 다시 계산하므로 숫자가 리포트와 정확히 같습니다.
- **리포트 · Publish**: 릴리스 태그 사이의 변경 내역을 포함한 리포트 페이지를 만들어 사내 위키에 Publish하고, 리소스 표를 갱신합니다.
- **다중 SoC**: 보드 드라이버를 플러그인으로 분리해 여러 칩셋 보드를 지원하고, 서버가 접속할 수 없는 보드는 외부에서 측정한 결과를 가져와(import) 같은 비교·추이 화면에서 봅니다.
